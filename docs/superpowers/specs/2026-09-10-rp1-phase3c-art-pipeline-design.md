**Status:** draft

## 1. Purpose and scope

`docs/palette.md` §1 states a rule — every pixel in `assets/` is one of Apollo's
46 colours — and then admits that "until those exist, the rule is honoured by
hand." Five deliberately off-palette debug swatches currently sit under a named
exemption. This phase replaces them with real art and makes the rule mechanical.

**The deliverable, stated as a single sentence:** `assets/` contains only
Apollo-quantized art derived from committed third-party sources by a
reproducible tool, and CI gate 6 makes an off-palette pixel unmergeable.

### 1.1 In scope

- Two CC-licensed art sources, committed under `assets/_source/`
- `tools/palette_map.gd`: a colour -> Apollo, in OKLab, with overrides
- `tools/quantize.gd`: slice sheets, quantize, write `assets/`
- `tools/check_palette.sh` -> `tools/check_palette.gd`: CI gate 6
- `tools/palette/apollo.json`: the palette as data, with a doc-drift test
- Deleting `tools/make_placeholder_art.gd` and the swatch exemption
- Recording the §6 Elin validation result measured during design

### 1.2 Out of scope

Autotiling and transition tiles, walk-cycle *animation* (Bukket's frames are
imported; nothing animates until Phase 6), the data-authored zone and
`AnimalSystem` (**Phase 4**), save wiring (**Phase 5**), and any change to
`ZoneRenderer`, `EntityRenderer` or `TilesetBuilder` — see §4 for why none is
needed.

The remaining §6 Elin validation screenshots are out of scope: they need someone
to run the game. §7 records what one screenshot established and what it did not.

### 1.3 Success criteria

- `./tools/check_palette.sh` passes, and has been seen to fail
- No file under `assets/` outside `_source/` contains an off-palette pixel
- Re-running `tools/quantize.gd` reproduces the committed PNGs byte-identically
- The existing 163 tests stay green with no renderer change
- `tools/make_placeholder_art.gd` and the `palette.md` §4 exemption are gone

## 2. The central bet

**Import is a transform, not a copy.** Third-party art enters the repository
twice: once as downloaded, and once as the project can actually use it. The
second is derived from the first by a committed tool, so it can be re-derived.

This is the same bet the project already made about content — `TilesetBuilder`
assembles a `TileSet` at runtime rather than committing a hand-edited `.tres`,
because a hand-edited artifact is a code change in all but name. A hand-edited
PNG is the same problem in a different file format.

The bet has a specific payoff. `palette.md` §2 marks the palette **provisional**,
pending a validation that is still open (§7). If the palette changes, everything
in `assets/` is regenerated by re-running one command. Without committed
sources, a palette change means re-downloading from URLs that may be dead and
redoing the colour work by hand — which is to say, it would never happen, and
"provisional" would quietly become permanent by attrition.

## 3. Art sources

| Source | Covers | Size | Licence |
|---|---|---|---|
| [Buch, Outdoor 32x32](https://opengameart.org/content/outdoor-32x32-tileset) | `grass`, `water`, `oak_tree` | 32x32 | CC0 |
| [Bukket Games, Top-Down RPG Character Sprites](https://opengameart.org/content/top-down-rpg-character-sprites) | `player`, `rabbit` | 32x64 frames | CC-BY 3.0 |

Both are recorded in `assets/CREDITS.md` and in the per-folder `LICENSE.txt`.
For Buch that is policy; for Bukket it is a licence condition, and the
distinction is noted in `CREDITS.md` so nobody later "tidies away" a required
attribution.

### 3.1 Why not Kenney

Every prior document names Kenney as the intended source. **Every Kenney
top-down pixel pack is 16x16** — Roguelike/RPG pack, RPG Urban Pack, the Tiny
series. RP1's tile size is 32x32.

Upscaling 16x16 art 2x and keeping 16x16 art at 2x camera zoom produce
*identical* screen output: one source pixel becomes a 2x2 block either way. Both
therefore discard the only thing 32x32 buys over 16x16, which is detail density.
Since a native 32x32 CC0 source exists, Kenney is not the cheaper option — it is
the same option with detail thrown away. The stale references are corrected in
§8.

### 3.2 Why the character source is CC-BY and not CC0

Eldiran's CC0 32x32 characters were selected during design and then rejected on
evidence. A screenshot of Elin — the stated visual reference — measures its
characters at roughly **32 wide by 64 tall**, chibi-proportioned. `CLAUDE.md`'s
existing 32x64 constant is correct and does not change.

No CC0 set at that proportion was found. Bukket's frames are exactly 32x64 with
four-frame walk cycles in three directions plus mirroring, under CC-BY 3.0 —
permitted by the `CREDITS.md` policy table with attribution. The trade is an
attribution obligation in exchange for matching the reference; CC-BY-SA options
such as LPC were not considered further, since `CLAUDE.md` flags share-alike as
a commercial risk.

Source frames are `.bmp`. Conversion to PNG happens in the pipeline, not by
hand — see §5.2.

## 4. Why nothing in `src/` changes

Buch's pack ships as a single `sheet.png`. The obvious reading is that many
definitions must now share one texture at different offsets, which would mean
teaching `TilesetBuilder._region_size()` and its `EntityRenderer` counterpart to
honour `sprite_rect`'s origin — today both use only the size, documented as
"each definition currently owns its whole PNG".

The pipeline slices instead. `quantize.gd` crops each rect out of the sheet and
writes a separate PNG, so every definition still owns its whole PNG and the
rendering code is untouched.

This is not merely convenient. Stage 1 acceptance criterion 8 reads *"adding a
new tree type = adding one JSON file + one PNG, no code change"* — the criterion
the design plan calls "the real test of whether the architecture worked".
Sheet-plus-rects would weaken it to "one JSON file + a rect into a sheet". The
criterion survives intact because import absorbs the difference.

**What a later atlas migration would need**, recorded so the option stays open:
rect origins in the two `_region_size` sites, and a manifest that already
records every rect — which §5.1 commits regardless.

## 5. The pipeline

```
assets/_source/                     <- as downloaded, committed, .gdignore'd
  buch-outdoor/{sheet.png,LICENSE.txt}
  bukket-characters/{*.bmp,LICENSE.txt}
        |
        |   tools/quantize.gd  (build-time only, never shipped)
        |     1. read tools/import_manifest.json
        |     2. crop rect from source
        |     3. map distinct colours -> Apollo  (tools/palette_map.gd)
        |     4. binarize alpha
        |     5. write PNG
        v
assets/tiles/grass.png              <- 32x32, Apollo-only, committed
assets/objects/oak_tree.png
assets/characters/player.png
```

`assets/_source/.gdignore` stops Godot importing the sources, so they never
enter the PCK. `Image.load_from_file()` still reads them at build time; the
engine warning it emits ("this will not work on export") is correct and
irrelevant, since this path runs only under `-s`. That is worth a comment at the
call site, because it reads like a bug.

### 5.1 `tools/import_manifest.json`

The committed record of what came from where.

```json
{"slices": [
  {"source": "buch-outdoor/sheet.png", "rect": [0, 0, 32, 32],
   "out": "assets/tiles/grass.png"},
  {"source": "bukket-characters/template_w.bmp", "rect": [0, 0, 32, 64],
   "out": "assets/characters/player.png"}
]}
```

Every output under `assets/` is named here. The gate in §6 asserts that the two
sets agree, so an asset cannot be added by hand without the manifest knowing.

### 5.2 `tools/palette_map.gd`

A `class_name PaletteMap extends RefCounted`, holding all colour logic and no
file I/O, so it is unit-testable directly.

It maps the **distinct colour set**, not each pixel. Pixel art is flat-coloured
— `grass.png` has two colours; the whole Elin screenshot has 119,587, and real
sprite sheets have a few dozen. Mapping distinct colours is both faster and
strictly safer: identical source colours are guaranteed to map identically, so a
flat region can never speckle.

Distance is Euclidean in **OKLab**. The alternative, RGB Euclidean, picks
visibly wrong shades in dark greens and blues — precisely Apollo's Green ramp,
which §7 measures at 85% of an outdoor scene's pixels. `Color.srgb_to_linear()`
exists in 4.7.2; the remaining conversion is about 25 lines.

**Alpha is binarized at 128.** Under project-wide `Nearest` filtering, partial
alpha has no meaning, and "alpha is 0 or 255, never between" is an invariant the
gate can check. Fully transparent pixels keep their RGB but are exempt from the
palette check, which is what makes `process/fix_alpha_border=true` in the
`.import` files harmless.

**No dithering.** Dithering scatters noise through flat colour regions, which is
the opposite of what this art style is.

### 5.3 `tools/palette_overrides.json`

`palette.md` pulls two ways. §5 says pick the nearest palette step; §3 says
"shade within a ramp; do not mix ramps to make a shade — that is what produces
mud." A nearest-colour pass obeys §5 and can violate §3: a brown trunk's shadow
may land in the Red or Neutral ramp because that is where the nearest colour is.

Rather than encode a ramp-aware heuristic — which breaks on any multi-coloured
sprite, and a tree is a brown trunk plus a green canopy — the mapping stays
simple and gains a human escape hatch:

```json
{"overrides": [
  {"from": "3b6338", "to": "25562e",
   "why": "trunk shadow landed in Neutral; forced into the Green ramp"}
]}
```

`quantize.gd` prints a mapping report — source hex, Apollo hex, ramp, pixel
count — which is how a wrong mapping is found. Every override is one reviewable
line with its reason attached, and survives re-quantization. The alternative,
hand-editing the output PNG, hides the decision in a binary file and loses it
the next time anything is regenerated.

### 5.4 The palette as data

Apollo currently exists only as prose in `palette.md` §3. Two tools need it, so
it moves to `tools/palette/apollo.json` with ramp names preserved.

Two copies of a colour list drift. `tests/test_palette.gd` parses the hex codes
back out of `docs/palette.md` §3 and asserts the two sets are identical, so the
drift is caught by the suite rather than by someone noticing a wrong green a
month later.

It goes in `tools/`, not `data/`. `data/` is game content loaded by
`ContentRegistry`; the palette is a build-time constraint the running game never
reads. (`ContentRegistry.CATEGORIES` is an allowlist, so `data/palette/` would
be silently ignored — safe, but wrong.)

## 6. CI gate 6

`tools/check_palette.sh` keeps the name `palette.md` §1 already promises, and
delegates to `tools/check_palette.gd` — bash cannot read PNG pixels.

It walks every PNG under `assets/` except `_source/` and fails on:

1. any pixel with alpha 255 whose RGB is not in the palette
2. any pixel whose alpha is neither 0 nor 255
3. any PNG not named as an `out` in the manifest

reporting file, x, y and hex for the first offenders of each kind.

**There is no exemption mechanism.** The swatches are deleted in this phase, so
nothing needs exempting, and `palette.md` §1 warns that a palette governing only
some art "is a style guide, not a constraint". An exemption list is how it
becomes one. The current swatch exemption is deleted rather than generalised.

Rule 3 is what stops the gate being bypassed by dropping a hand-made PNG into
`assets/` — it would be on-palette and still unreproducible.

## 7. The Elin validation (`palette.md` §6, item 1)

One screenshot was supplied during design and measured. This is a partial
result: §6 asks for 8-12 across biomes and times of day, and this is one sunny
meadow at midday — the most saturated-green scene the game has.

**The screenshot is not committed, and no future one may be.** `palette.md` §7
states that no Elin art, sprite, tile or asset is copied into this project, and
a screenshot is Elin art. Only the derived measurements below are recorded. This
constrains how §6 gets finished: measure, write down numbers, delete the image.
`.gitignore` gains a rule to make an accidental commit hard (§8).

| Measure | Result |
|---|---|
| Mean OKLab error to nearest Apollo colour | 0.056 |
| Median / p90 | 0.055 / 0.074 |
| Mean gap between adjacent steps within a ramp | 0.109 |
| Ramp usage by pixel share | green 85.1%, neutral 6.5%, tan 4.6%, gold 3.5%, blue 0.0% |
| Chroma change after quantization | **+37.1%** |
| Lightness change | +0.6% |

**Reading it.** Error at roughly half a ramp step is a good result — quantizing
costs about half a shade of precision. The chroma figure is not: Apollo renders
the scene 37% more saturated, with the dominant meadow greens (`#33462a` ->
`#25562e`) gaining 49-67%. That contradicts `palette.md` §2's stated reason for
choosing Apollo, "muted and naturalistic rather than saturated and punchy". For
the Green ramp carrying 85% of an outdoor scene, Apollo is the punchier of the
two. Separately, Blue and Purple — 12 of 46 colours — do essentially nothing
outdoors, which sharpens the headroom cost §2 already accepted.

**Why this does not change the palette today.** §6's method measures the wrong
surface. Elin's on-screen colour is base sprites multiplied by real-time
lighting, as §2 itself notes; the olive cast is partly shadow, not pigment, so
Elin's underlying art is very likely more saturated than measured here. RP1 has
no lighting in Stage 1, which means flatter, more saturated base art may be the
correct compensation rather than an error. Changing a load-bearing constraint on
one screenshot, measured through a known-biased method, is not warranted.

Apollo therefore stands, still marked provisional. `palette.md` §6 gains these
numbers, the method, and the lit-output caveat, so the next person inherits
evidence instead of an open question.

**Optional, and marked as such in the plan:** a small `tools/palette_report.gd`
reusing `PaletteMap` would let the remaining screenshots be measured with the
project's own tooling rather than the throwaway scripts used here. Worth doing
only if it stays under about 40 lines.

## 9. Testing

TDD throughout, per `CLAUDE.md`.

| Test | Asserts |
|---|---|
| `tests/test_palette_map.gd` | OKLab nearest picks the expected step; overrides take precedence; alpha binarization at the 128 boundary; mapping is deterministic across runs |
| `tests/test_palette.gd` | `apollo.json` and `palette.md` §3 agree; 46 unique colours |
| `tests/test_import_manifest.gd` | every `out` has a matching content definition, and each sliced PNG's dimensions match the `sprite_rect` its JSON declares |

The third covers the one seam this phase creates where the manifest and
`data/*.json` can silently disagree: a rect resized without updating the content
file renders a sprite at the wrong size, and nothing else would catch it.

The 163 existing tests must stay green **without modification**. That is the
evidence for §4 — if slicing were wrong, renderer tests would need changing.

Every new gate assertion is to be seen failing before it is trusted, as with the
Phase 3b smoke work.

## 10. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Buch's pack has no usable tree (the description says "stumps") | Medium | Resolved in the plan's first task by inspecting the sheet, not deferred. A second CC0 source fills the one gap if needed. |
| Two authors' styles clash | Medium | Quantizing both through the same 46 colours is itself a strong unifier. Reviewed by eye once real art is in; the fallback is redrawing the two characters. |
| Quantization produces mud on a specific sprite | Medium | The override table (§5.3), which exists for exactly this. |
| Apollo is the wrong palette (§7) | Low-Medium | Committed sources make a later palette change a re-run rather than a rewrite. This is the risk §2 of this document is designed around. |
| `.bmp` sources import badly or inconsistently | Low | Conversion happens in `quantize.gd` against `Image`, the same path as PNG; the output is a committed PNG either way. |
